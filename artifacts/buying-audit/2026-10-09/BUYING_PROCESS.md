## What happens if it is not delivered

**Brief — published policy:** the customer can cancel by email before work begins for a full refund. Once bespoke work has begun, the published terms provide exceptions for failure to deliver the agreed scope and remedies that cannot lawfully be excluded. For a source issue after payment, staff must notify the buyer and offer a revised date or full refund if no alternative scope is agreed. These are statements of the site's terms, not a new legal interpretation. [Saved terms screen](terms-desktop.png); live [Business Terms](https://www.caregist.co.uk/terms), sections 6–7.

**Customer action:** contact support@caregist.co.uk with the Stripe receipt/payment reference, agreed scope/date and what is missing. Do not pay again. This is what the return page directs; it is not proof that the mailbox has been monitored or a response received.

**Staff action required:** locate and reconcile the payment/order, distinguish failed generation from failed email or failed download, contact the buyer, obtain agreement to any revised date/scope, and issue any required refund using the actual merchant payment mechanism. For Stripe payments, an authorised staff operator can issue the refund through Stripe Dashboard/API and must track its final status; refunds can remain pending or fail. Recording a webhook does not initiate a refund or prove money reached the customer. [Stripe refund documentation](https://docs.stripe.com/refunds).

## Broken, missing and incomplete

1. **Refund handler broken on actual schema — repaired locally.** `_handle_refund` attempted a refund insert into `billing_operations`, which has neither `amount_gbp`/`metadata` columns nor a refund operation/status or the assumed conflict key. Original real-Postgres run: three failures, one dead-letter pass, [failure log](refund-tests.log). Removed the incompatible write; refund events use the existing audit record and entitlement updates, with webhook dedup already handled by `stripe_processed_events`. New tests use real audit SQL and verify records. Refund audit writes now use strict mode. A real missing-audit-table test proves the order change and processed-event marker roll back, allowing retry; other callers retain their existing best-effort behaviour.
2. **Failed-generation refund matching — repaired locally.** Validated payment/consent evidence is carried across rollback into the independent failure recorder. Refund and generation use the same transaction payment lock; full-refund audit evidence is consulted before generation and when recording failure. Both refund orderings reject checkout replay and create no files, tokens or email. Existing unmatched legacy rows still require reconciliation; the direct-handler characterisation test is explicitly not a pass for legacy-order matching.
3. **Generator contract differs from today's enquiry criteria.** Live coverage captures provider group and service type. Checkout/generator scope carries geography, time window and shortlist target, with no selected provider-group/service filter in its request contract. Our unfiltered historical Southampton fixture includes clinics/GPs as well as care homes. This does not prove a manually produced, independently checked pack is wrong; it means the dormant generator cannot be accepted as fulfilment of every current picker selection without additional scoped production/validation.
4. **Qualification questions missing from generated sample.** Live sales copy promises one per shortlisted organisation. PDF/CSV contain facts, reasons, limits and links, but no qualification-question field or per-entry question. General limitations are not a replacement.
5. **Coverage count language overstates readiness in the observed production API — repaired locally.** Saved live JSON says a scope is “ready”, `canCheckout:true`, and 157 providers is “enough for the full ranked shortlist”. The repaired helper retains count bands but always returns `canCheckout:false`, states matching-provider counts and directs scope review without promising a ranked product. This change does not enable ordering.
6. **Weekly Digest remains incomplete.** Enquiry CTA works as a link; no approved product-specific terms, payment/delivery agreement, four-week sequence, acceptance or missed-week recovery proof was found. Draft terms/invoice documents cannot serve as approvals or payment evidence.
7. **Human handoffs unverified.** A named owner, mailbox receipt, acknowledgement, accepted written scope, actual payment, independent pack review, delivered email, valid private-file download and buyer resolution are absent from this audit. These can be engineering-tested with authorised synthetic customers; a genuine paid customer is not a prerequisite.
8. **Documentation is stale.** Existing warroom summaries still describe older releases and previously unmerged fulfilment code. This dated evidence supersedes those statements for this buying audit; it does not open commercial gates.
9. **Remaining interruption/commit recovery gap.** Post-upload database-write failures are now exercised and retain payment/consent through the recorder. An outer transaction commit failure, process termination before recording, orphan private uploads and complete reconciliation after such interruption are not established by these tests. Refund audit guards prevent subsequent access, but accounting/order state may still require manual reconciliation. No automatic external-upload cleanup was added.
10. **Dormant generation source is not verified as deployable.** Runtime wiring still reads mirrored NDJSON snapshot files; its module documentation explicitly requires canonical Postgres or an edition index before enabling the feature. A generated fixture and successful build do not prove the full source is present in a serverless deployment. Checkout source checks must remain closed when it is absent.

Additional reviewed repairs preserve existing non-null payment identity and compare immutable consent before every entitlement path. Historical full-dataset replay now uses the same payment lock and durable refund check. Separate database connections exercise both lock orderings: a refund that wins prevents a token/email grant; checkout that wins is subsequently revoked. This does not reintroduce the retired dataset offer.

## Reproduce

From the repository, run the file list recorded in `final-tests.xml` using `.venv/bin/python -m pytest`; set both `CAREGIST_TEST_DATABASE_URL` and `CAREGIST_TEST_ADMIN_DATABASE_URL` to a disposable local PostgreSQL/PostGIS admin server. The fixtures create isolated databases/roles and apply the full schema. Never point these tests at production.

For browser tests: in `frontend`, `CAREGIST_E2E_BASE_URL=https://www.caregist.co.uk node_modules/.bin/playwright test e2e/territory-journey.spec.ts --workers=1`. The test intercepts coverage and does not submit an enquiry or payment. `capture-browser.cjs` makes read-only page requests and a public coverage calculation, saving screenshots and actual response JSON. `PYTHONPATH=. .venv/bin/python artifacts/buying-audit/2026-10-09/render_fixture.py` regenerates the illustrative packs; their fixture edition is 2026-02-18 and must not be passed off as current evidence.
