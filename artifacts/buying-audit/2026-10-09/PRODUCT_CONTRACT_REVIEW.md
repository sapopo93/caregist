## Defects and bounded acceptance tests

1. **Missing per-entry qualification question (critical contract defect).** Add a source-grounded, buyer-useful qualification question for every delivered shortlist entry, or remove the promise from the page and order scope. Do not invent operational facts such as vacancies, budgets or intent. **Acceptance:** generate the smallest supported 25-entry and a 50-entry pack; verify every CSV row and corresponding report entry has exactly one non-empty qualification question tied to the stated buyer criteria, alongside the fact, reason, evidence and uncertainty. Include an unsupported-fact fixture and confirm the question asks the buyer to verify rather than asserting the unsupported fact. Confirm no row is silently omitted or padded. These are proposed acceptance checks, not tests run in this review.

2. **Picker criteria mapping is not demonstrated (critical contract defect).** Establish and expose the exact mapping from buyer input to inclusion/ranking and to each qualification question. Current observed input consists of region, signal category (`buyerType`) and optional service type; the generator's source contract is territory/window/shortlist target and event-based ranking. **Acceptance:** for each selectable buyer type and service filter, use a small labelled fixture with known matching and non-matching rows; assert request payload, API filter, resulting included/excluded records, ranking rationale and question all reflect that selection. Add a custom buyer criterion only if it is actually captured and applied; otherwise label these controls as signal filters and use “agreed criteria” only for a separately recorded scope.

3. **`ready` / `canCheckout` conflicts with customer-facing availability language (high severity).** Saved API evidence reports `ready` and `canCheckout:true` for 157 London matches; the screen says coverage does not confirm availability, offers email review, and states online ordering is unavailable. `canCheckout` is not consumed by the picker. **Acceptance:** test one ready, one partial and one insufficient response. Assert the API field name and explanatory copy consistently describe coverage eligibility versus actual checkout; assert no result state implies order/payment availability when the commercial gate is off; and assert the UI never offers a checkout action unless the actual checkout gate is open. Verify enquiry wording remains “request/review,” creates no order, and represents no payment as completed.

4. **Weekly Digest remains legally gated (release blocker for that product, not evidence of an approved product).** The solicitor-review draft records the mismatch between public claims and terms and several unresolved founder decisions. **Acceptance:** before publishing or taking payment, obtain the required solicitor/founder decision and approved terms version/hash; reconcile site promises to evidenced digest capabilities, especially changes/closures and per-item links; then verify displayed price, scope, delivery, cancellation/refund and no-renewal terms against that approved version. No such approval or payment is asserted here.
