## Step 2 — rating-source resolver

`api/services/rating_resolver.py`. Evidence comes from the API, the ratings file (with inherited flag, sha256 and edition) and optional dated CQC-page observations. The resolver returns one of four statuses:

- `current`: the newest published value
- `inherited`: published before this registration, or flagged inherited
- `unresolved`: an undated or same-date conflict, or an inherited value contradicted by one earned under this registration. These are never shown.
- `none`: no published rating

Frozen fixtures `tests/fixtures/rating_audit_2026_10_22.json` were built by `artifacts/report-readiness/2026-10-24/build_rating_fixtures.py` from the audit packet, the ODS inherited flags and registration dates read from the database.

| Fixture group | Result |
|---|---|
| 20 file-backed | file value, date, sha256 and edition retained. 19 `current`; Tillingham `inherited` (file flag Y; predates its 2023 registration) |
| 5 conflicts | St Stephens, Althorp Grange, Chesser → `current` Requires improvement from the newer file (older API value cannot override). Irchester 170 and Check House → `unresolved`, omitted. |
| 5 unrated | `none`; the "Inspected but not rated" sentinel is kept in evidence but never chosen |
| Post-snapshot | Chestnuts: without a page observation it stays file Inadequate (current as of the 2 Oct edition). With the 13 Oct observation it becomes Requires improvement, `newer_than_file_edition=true`. |
| Check House page observation | `inherited` Outstanding, never `current` |

There is a deliberate trade-off. Irchester 170 and Check House have the same data shape, but CQC's site shows the file value for one and only the inherited rating for the other. The resolver therefore leaves both unresolved instead of guessing. Irchester's correct Good is withheld until a page observation is supplied.

**Brief wiring** (`territory_brief.py`, `territory_brief_render.py`):
- Ratings in tables, the Appendix A narrative ("inherited from a predecessor"), evidence items (`source_field resolved_rating.cqc_ratings_file`, `source_edition` with file sha256) and Appendix B coverage all use the resolution.
- PDF Appendix C covers rating provenance and names the omitted conflicts.
- The CSV gains 10 `rating_*` columns; JSON gains `rating_resolution`.
- Rating groups (Inadequate / Requires improvement) admit only `current` values equal to the group, and every exclusion is listed.
- A file value never creates a `rating_changed` event.
- Sample: `step2/fixture_territory_brief_ri.{pdf,csv,json}`. In it, PDF, CSV and JSON agree on one edition and hash (test `test_pdf_csv_and_json_agree_on_the_same_resolution`).

## Known gaps

1. The resolver is not wired into paid delivery, the public coverage count or the directory display. Search still shows API-first values (3 precedence defects, 2 unresolved values shown in the 1a sample).
2. The 51 CQC-deregistered rows are still ACTIVE in the directory. The generators exclude them, but the directory itself needs a reconciliation run, which is a production write and outside this work.
3. The database does not store the ratings file's inherited flag, so inheritance is detected from the registration date only. The Brief and P12 paths that read the ODS do use the flag.
4. Dual registrations are not merged in CareGist outputs (for example, Trymview Hall appears twice in the BS6 scan) or in the CareGist benchmark columns.
5. The look-alike-successor rule (name + postcode, 120 days) is a heuristic and only ever moves rows to `unresolved`, never to closure.
6. The 70% bed-share reference is unverified and contradicts CQC's own register. The 1 Oct file cutoff is still unverified.
7. No live CQC API or website re-check was made. All comparisons are as at 20 Oct (export) and 2 Oct (file).
